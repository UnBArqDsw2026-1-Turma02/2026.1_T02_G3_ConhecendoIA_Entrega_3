# 3.1.6 Observer

## 1. Introdução ao Padrão Observer
O padrão de projeto Observer é um padrão comportamental que define uma relação de dependência entre objetos, permitindo que múltiplos componentes sejam automaticamente notificados sempre que ocorrer uma alteração no estado de um objeto principal.

Esse padrão é amplamente utilizado em sistemas orientados a eventos, mecanismos de notificações, redes sociais, chats, aplicações reativas e arquiteturas desacopladas. Seu principal objetivo é permitir comunicação dinâmica entre objetos sem criar dependências rígidas entre eles.

No Observer, o objeto principal — chamado de `Subject` — mantém uma lista de observadores (`Observers`) inscritos. Sempre que um evento relevante ocorre, o `Subject` dispara notificações para todos os observadores registrados.

---

## 1.1. Problema que o Observer Resolve
Em aplicações tradicionais, quando diversos componentes precisam reagir a uma mesma alteração, o objeto principal acaba precisando conhecer diretamente todos os módulos dependentes, gerando forte acoplamento e dificultando a escalabilidade do sistema.

O padrão Observer resolve os seguintes problemas:

* **Alto Acoplamento:** O objeto observado não precisa conhecer detalhes internos dos observadores.
* **Propagação Manual de Eventos:** Automatiza o envio de atualizações para múltiplos componentes.
* **Baixa Escalabilidade:** Permite adicionar novos observadores sem modificar o código do `Subject`.
* **Dificuldade de Manutenção:** Centraliza o gerenciamento de notificações em uma única estrutura.

---

## 1.2. Estrutura e Participantes
O padrão Observer envolve os seguintes elementos:

* **Subject (Observado):** Classe responsável por armazenar e gerenciar os observadores inscritos.
* **Observer (Observador):** Interface implícita que define o método `atualizar()`.
* **ConcreteObserver:** Implementações concretas que executam diferentes ações ao receber notificações.
* **Client:** Responsável por criar os objetos, registrar observadores e disparar eventos.

---

## 1.3. Variações Comuns
* **Push Model:** O `Subject` envia os dados completos diretamente para os observadores durante a notificação.
* **Pull Model:** Os observadores recebem apenas o aviso da alteração e consultam os dados posteriormente.
* **Observers Dinâmicos:** Observadores podem ser adicionados ou removidos em tempo de execução.

## 1.5. Como Funciona
* O `Client` cria o objeto observado (`Subject`).
* Os observadores são registrados através do método `inscrever()`.
* Quando uma interação relevante ocorre, o `Subject` executa o método `notificar()`.
* O método `notificar()` percorre todos os observadores cadastrados.
* Cada observador executa sua própria lógica através do método `atualizar()`.
* Observadores podem ser removidos dinamicamente utilizando `desinscrever()`.

---

## 1.6. Benefícios
* Reduz o acoplamento entre os componentes do sistema.
* Facilita a extensão da aplicação.
* Permite múltiplos mecanismos de reação para um mesmo evento.
* Favorece arquiteturas orientadas a eventos.
* Simplifica manutenção e evolução do código.

---

## 1.7. Desvantagens
* O fluxo de execução pode se tornar mais difícil de rastrear.
* Muitos observadores podem impactar performance em sistemas grandes.
* Existe risco de efeitos colaterais caso múltiplos observadores reajam simultaneamente ao mesmo evento.

---

# 2. Aplicação do Padrão Observer no Projeto "ConhecendoIA"
No projeto "ConhecendoIA", o padrão Observer é aplicado no sistema de interações sociais da plataforma, permitindo que diferentes serviços de notificação reajam automaticamente a eventos realizados em publicações da comunidade acadêmica.

A implementação possibilita que curtidas e comentários em posts disparem notificações independentes para diferentes canais, como Push Notification e E-mail, sem que o objeto principal precise conhecer detalhes internos de cada mecanismo de envio.

**Localização:** `projeto/src/observers/NotificacaoObserver.js`

---

## 2.1. Contexto do Problema
Dentro da plataforma, usuários podem interagir com postagens realizadas por professores e estudantes através de curtidas e comentários. Sempre que uma interação ocorre, diferentes serviços precisam ser acionados automaticamente para informar o autor da publicação.

Sem o Observer, a classe responsável pelo post precisaria chamar manualmente cada sistema de notificação, criando forte acoplamento entre o módulo de publicações e os serviços externos de comunicação.

Além disso, qualquer novo tipo de notificação exigiria modificações diretas no código principal do sistema, dificultando manutenção e escalabilidade.

---

## 2.2. Solução com Subject e Observers
A implementação utiliza a classe `Subject` como núcleo do gerenciamento de observadores. Ela mantém uma lista dinâmica de serviços inscritos e fornece métodos para registrar (`inscrever`), remover (`desinscrever`) e notificar (`notificar`) os observadores.

Os observadores concretos implementam diferentes estratégias de comunicação:

* `NotificacaoPushObserver`: Responsável por notificações instantâneas via push.
* `NotificacaoEmailObserver`: Responsável pelo envio de notificações por e-mail.

A comunicação ocorre através do método `atualizar()`, que recebe os dados do evento disparado pela publicação.

```javascript
class Subject {
  constructor() {
    this.observers = [];
  }

  inscrever(observer) {
    // garante que o observer tem atualizar()
    if (typeof observer.atualizar !== "function") {
      throw new Error("Observer deve implementar o método atualizar()");
    }
    this.observers.push(observer);
  }

  desinscrever(observer) {
    this.observers = this.observers.filter(obs => obs !== observer);
  }

  notificar(dados) {
    this.observers.forEach(obs => obs.atualizar(dados));
  }
}

class NotificacaoPushObserver {
  atualizar({ tipo, post, atorInteracao, detalhe = null }) {
    const autorDoPost = post.autor.nome;

    if (tipo === "comentario") {
      console.log(
        `🔔 [PUSH para ${autorDoPost}]: ${atorInteracao.nome} comentou. Disse: "${detalhe}"`
      );
    } else if (tipo === "curtida") {
      console.log(
        `🔔 [PUSH para ${autorDoPost}]: "${post.titulo}" recebeu curtida de ${atorInteracao.nome}.`
      );
    }
  }
}

class NotificacaoEmailObserver {
  atualizar({ tipo, post, atorInteracao }) {
    const autorDoPost = post.autor.nome;

    if (tipo === "comentario") {
      console.log(
        `📧 [E-MAIL para ${autorDoPost}]: Novo comentário de ${atorInteracao.nome} em "${post.titulo}".`
      );
    }
  }
}
```

---

## 2.3. Funcionamento da Implementação
No fluxo principal do sistema, um post acadêmico funciona como o `Subject`, permitindo que serviços de notificação sejam registrados dinamicamente.

Quando uma curtida ou comentário é realizado, o post dispara uma notificação contendo informações da interação, como:

* Tipo do evento (`curtida` ou `comentario`)
* Usuário que realizou a interação
* Post afetado
* Conteúdo do comentário (quando existir)

Os observadores recebem esses dados e executam suas ações independentemente.

```javascript
const profAltair = new Usuario(1, "Prof. Altair");
const alunoJoao  = new Usuario(2, "João Silva");
const alunaMaria = new Usuario(3, "Maria Souza");

const postRedesNeurais = new Post(
  101,
  "O que é um Perceptron?",
  "...",
  profAltair
);

const servicoPush  = new NotificacaoPushObserver();
const servicoEmail = new NotificacaoEmailObserver();

postRedesNeurais.inscrever(servicoPush);
postRedesNeurais.inscrever(servicoEmail);

postRedesNeurais.adicionarCurtida(alunoJoao);

postRedesNeurais.adicionarComentario(
  alunaMaria,
  "Excelente explicação!"
);

postRedesNeurais.adicionarComentario(
  profAltair,
  "Fico feliz em ajudar!"
);

// Exemplo: desinscrever push quando usuário desativa notificações
postRedesNeurais.desinscrever(servicoPush);

console.log("Push desativado para este post.");
```

Nesse modelo, o sistema de publicações permanece desacoplado dos mecanismos de envio de notificações. Novos serviços — como SMS, WebSocket ou notificações em tempo real — podem ser adicionados futuramente apenas criando novos observadores que implementem o método `atualizar()`, sem alterar a lógica principal da aplicação.

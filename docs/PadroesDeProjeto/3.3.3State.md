## 1. Introdução
O padrão de projeto State é um padrão comportamental documentado pela Gang of Four (GoF) que permite que um objeto altere o seu comportamento interno quando o seu estado interno muda. O objeto parecerá ter mudado de classe [[1]](#ref1). Em essência, o padrão encapsula estados em classes separadas e delega as tarefas para o objeto que representa o estado atual.

### 1.1 O problema que o State resolve
Sistemas que dependem de muitos estados tendem a acumular estruturas condicionais complexas (como extensos blocos de `if/else` ou `switch/case`) para controlar como um objeto deve reagir a um comando dependendo do seu status atual. À medida que o sistema cresce, adicionar um novo estado ou alterar regras de transição torna o código frágil e difícil de manter. O padrão State resolve isso extraindo o código relacionado a cada estado específico para classes independentes, descentralizando a lógica condicional [[2]](#ref2).

### 1.2 Estruturas e participantes
O padrão State baseia-se em três componentes primários [[1]](#ref1):
* Context (Contexto): Define a interface de interesse para os clientes e mantém uma instância de uma subclasse ConcreteState que define o estado atual.
* State (Estado): Uma interface ou classe abstrata que encapsula o comportamento associado a um estado específico do Context.
* ConcreteState (Estado Concreto): Subclasses que implementam os comportamentos específicos para os diferentes estados do Context.

### 1.4 Como funciona
O Context recebe solicitações do cliente (ex: criar um post) e delega essa requisição para o objeto State que ele mantém em memória no momento. Quando as condições de negócio são atingidas (ex: fornecer credenciais corretas), o estado atual atualiza a referência dentro do Context para uma nova instância de ConcreteState, realizando a "transição de estado" de forma limpa e transparente para o cliente [[3]](#ref3).

## 2. Aplicação do Padrão State no projeto Conhecendo IA
No contexto do fórum web Conhecendo IA, o sistema exige um controle de acesso robusto, incluindo registro de contas e níveis de permissão. O padrão State foi aplicado para gerenciar a sessão do usuário, alterando as permissões dinamicamente conforme ele autentica, desloga ou navega pela plataforma.

### 2.1 Classes e funções
O ecossistema de controle de sessão foi modelado com as seguintes estruturas:
* `UserSession` (Context): Representa a sessão ativa do usuário no fórum. Ela mantém o estado inicial como visitante e repassa todas as ações do portal (como `viewContent`, `createPost`, `authenticate`) para o objeto de estado vigente.
* `UserState (State)`: A classe base abstrata que dita o contrato de métodos. Se uma ação não for sobrescrita por uma subclasse concreta, o método base lança um erro ou retorna _denied(), protegendo o sistema por padrão.
* ConcreteStates:
    * `GuestState`: Estado inicial. O usuário só pode visualizar conteúdo ou tentar autenticar.
    * `MemberState`: Representa um usuário logado padrão. Possui permissões para comentar, curtir e criar tópicos próprios.
    * `ModeratorState`: Representa a equipe técnica de moderação, com capacidade de deletar conteúdos inadequados de terceiros.
    * `AdminState`: Acesso irrestrito ao sistema, incluindo o poder de banir usuários e promover membros.

### 2.2 Exemplo de uso das classes e funções
O uso transparente do contexto permite que as transições ocorram sem que a classe cliente precise validar as permissões via condicionais:

```JavaScript
const session = new UserSession(); // Inicia como GuestState (Visitante)

// Ação negada pelo estado atual
session.createPost(); 

// O estado de visitante processa a transição e altera o contexto para MemberState
session.authenticate({ username: "joao", password: "123456" });

// Agora as mesmas ações possuem comportamentos liberados
session.createPost(); 
session.commentOnPost(); 

// A sessão retorna para GuestState
session.logout();
```

## 2.3 Vantagens no Projeto
* Isolamento de Permissões: O sistema de login e as regras de quem pode ou não postar no fórum estão totalmente separadas por classe. Se houver uma falha de lógica na classe do Visitante, isso não concederá acidentalmente privilégios de Administrador.
* Fácil Expansão de Níveis: A criação de um novo tipo de conta no fórum (como um "Membro Premium" com acesso a tópicos exclusivos) exigiria apenas a criação de um novo arquivo de estado, sem tocar nas classes já estabilizadas.

## 3. Benefícios
A implementação geral do padrão State traz melhorias significativas à arquitetura do software [[1]](#ref1)[[2]](#ref2):
* Princípio de Responsabilidade Única: O código relacionado a um estado particular fica concentrado em um só lugar.
* Transições Explícitas: A troca de estado é feita instanciando novas classes de forma objetiva, mitigando bugs de inconsistência de variáveis isoladas (ex: um campo `isAdmin = true` esquecido em `false`).
* Simplificação do Código Contextual: Elimina a necessidade de grandes blocos de controle de fluxo condicional associados a "tipos de usuário" na controladora principal.

## 4. Desvantagens
Apesar dos benefícios organizacionais, o padrão apresenta alguns desafios [[3]](#ref3):
* Volume de Classes: Pode ser considerado um exagero (overengineering) caso as regras de negócio tenham pouquíssimos estados que quase nunca mudam de comportamento, gerando uma quantidade excessiva de arquivos e classes simples.
* Dependência entre Estados: Se os estados precisarem conhecer e instanciar ativamente os próximos estados (como visto no `GuestState` chamando `new AdminState()`), cria-se um acoplamento entre as subclasses concretas.

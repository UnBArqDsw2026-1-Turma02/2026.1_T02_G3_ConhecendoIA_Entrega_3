# 3.3.2 Observer

## 1. Introdução ao Padrão Observer
O padrão Observer é um padrão de projeto comportamental que define uma dependência do tipo um-para-muitos entre objetos, de modo que, quando um objeto muda de estado, todos os seus dependentes são notificados e atualizados automaticamente.

Este padrão é útil quando existe a necessidade de manter diferentes partes do sistema sincronizadas sem acoplá-las diretamente, especialmente em cenários orientados a eventos, notificações e atualizações reativas.

### 1.1. Problema que o Observer Resolve
Imagine que uma entidade central do sistema, como uma postagem de fórum, pode receber interações diferentes, como curtidas e comentários. Sempre que isso acontece, outros serviços precisam reagir, por exemplo, enviando notificações push ou e-mails. Se essa lógica for implementada diretamente dentro da classe principal, ela ficará excessivamente acoplada aos serviços de notificação, dificultando manutenção, testes e extensões futuras.

O Observer resolve esse problema separando a entidade principal (o "Subject") dos objetos que precisam reagir às mudanças (os "Observers"). Assim, o Subject apenas mantém uma lista de inscritos e notifica todos eles quando um evento relevante acontece, sem precisar conhecer detalhes internos de cada reação executada.

### 1.2. Estrutura e Participantes
O padrão Observer geralmente envolve os seguintes participantes:

* **Subject (Sujeito):** Mantém uma lista de observadores, oferece operações para inscrever e desinscrever observers, e dispara notificações quando ocorre uma mudança de interesse.
* **Observer (Observador):** Define uma interface comum para os objetos que devem ser notificados sobre alterações no Subject.
* **ConcreteObserver (Observador Concreto):** Implementa a lógica específica executada quando uma notificação é recebida.
* **ConcreteSubject (Sujeito Concreto):** Representa a entidade real observada, sendo responsável por disparar as notificações aos observers inscritos.

**Explicação do diagrama**
* O `Client` cria o `ConcreteSubject` e os `ConcreteObservers`.
* O `Subject` mantém uma coleção de observers inscritos.
* O `Subject` disponibiliza operações como `attach()`, `detach()` e `notify()`.
* Quando há uma mudança relevante no `ConcreteSubject`, ele executa a notificação de todos os observers.
* Cada `ConcreteObserver` reage ao evento de acordo com sua própria responsabilidade.

### 1.4. Como Funciona
1. **Definição do Subject:** Uma classe base ou estrutura central mantém uma lista de observers inscritos.
2. **Definição da Interface Observer:** Os observers compartilham um contrato comum, geralmente com um método como `update()` ou `atualizar()`.
3. **Inscrição dos Observers:** Os objetos interessados se registram no Subject para receber notificações futuras.
4. **Mudança de Estado ou Evento:** Quando algo relevante acontece no Subject, ele percorre sua lista de observers.
5. **Notificação:** Cada observer é chamado e executa sua própria reação ao evento recebido.
6. **Desinscrição (Opcional):** Um observer pode ser removido da lista caso deixe de ter interesse nas notificações.

### 1.5. Benefícios
* **Baixo Acoplamento:** O Subject não precisa conhecer detalhes internos dos serviços que reagem aos eventos.
* **Extensibilidade:** Novos observers podem ser adicionados sem alterar a lógica principal do Subject.
* **Reutilização:** Diferentes observers podem reagir ao mesmo evento de formas distintas, reaproveitando o mesmo mecanismo de notificação.
* **Organização por Responsabilidade:** Cada observer concentra um comportamento específico, como envio de push ou e-mail.
* **Aderência a Eventos do Domínio:** O padrão se encaixa bem em cenários onde ações do usuário disparam reações automáticas.

### 1.6. Desvantagens
* **Notificações em Cadeia:** Em sistemas maiores, o fluxo de notificações pode ficar difícil de rastrear.
* **Ordem de Execução:** Dependendo da implementação, a ordem de notificação dos observers pode influenciar o comportamento observado.
* **Sobrecarga com Muitos Observers:** Se muitos observers estiverem inscritos, cada evento poderá gerar múltiplas ações e aumentar o custo de processamento.
* **Risco de Reações Inesperadas:** Observers mal definidos podem introduzir efeitos colaterais difíceis de prever.

## 2. Aplicação do Padrão Observer no Projeto ConhecendoIA

No projeto **ConhecendoIA**, o padrão Observer foi aplicado para tratar notificações automáticas em interações do fórum. Sempre que uma postagem recebe uma curtida ou um comentário, os serviços inscritos são notificados para reagirem de forma independente, como no envio de push e de e-mail.

### 2.1. Informações do Projeto e Implementação
* **Link da aplicação (deploy):** ConhecendoIA Fórum (a funcionalidade está associada ao fluxo de interações e notificações do domínio do fórum)
* **Link da pasta do frontend (código):** [Frontend ConhecendoIA](https://github.com/UnBArqDsw2026-1-Turma02/2026.1_T02_G3_ConhecendoIA_Entrega_3/tree/main/frontend)
* **Links da implementação do Observer:**
  * Subject e Observers Concretos: `src/lib/observer.js`
  * Entidade observada no domínio: classe `Post`, responsável por disparar notificações em eventos como curtidas e comentários

### 2.2. Contexto do Problema no Fórum
No contexto do Fórum, uma postagem pode receber diferentes interações dos usuários. Quando isso acontece, o sistema precisa informar o autor do post e possivelmente outros interessados. Exemplos dessas reações incluem:

1. Enviar uma notificação push quando o post recebe curtida ou comentário.
2. Enviar um e-mail quando um novo comentário é publicado.
3. Permitir que certos canais de notificação sejam ativados ou desativados dinamicamente.

Se a classe da postagem implementasse diretamente todas essas reações, ela ficaria fortemente acoplada aos mecanismos de notificação. Isso dificultaria a manutenção e a adição de novos canais, como SMS, alertas internos ou integrações externas.

### 2.3. Solução com o Padrão Observer
Para resolver esse problema, foi adotado o padrão Observer:

* **Subject:** A classe `Subject`, em `src/lib/observer.js`, mantém o array `observers` e fornece os métodos `inscrever(observer)`, `desinscrever(observer)` e `notificar(dados)`.
* **Contrato dos Observers:** O método `inscrever()` valida se o objeto informado implementa `atualizar()`, garantindo que todos os observers respeitem o mesmo contrato de comunicação.
* **Observers Concretos:** Foram implementados observers especializados:
  * `NotificacaoPushObserver`: reage a eventos de curtida e comentário, exibindo mensagens de push para o autor da postagem.
  * `NotificacaoEmailObserver`: reage a eventos de comentário, exibindo mensagens equivalentes ao envio de e-mail.
* **Post como Sujeito Observado:** A entidade `Post` atua como sujeito concreto no domínio. Ao receber interações como `adicionarCurtida()` e `adicionarComentario()`, ela aciona o mecanismo de notificação para todos os observers inscritos.
* **Desinscrição Dinâmica:** O código também demonstra a remoção de observers com `desinscrever()`, permitindo desligar um canal de notificação sem alterar o restante da estrutura.

### 2.4. Exemplo da Implementação

**a) Subject e Observers Concretos (`src/lib/observer.js`)**
```javascript
class Subject {
  constructor() {
    this.observers = [];
  }

  inscrever(observer) {
    if (typeof observer.atualizar !== "function") {
      throw new Error("Observer deve implementar o método atualizar()");
    }
    this.observers.push(observer);
  }

  desinscrever(observer) {
    this.observers = this.observers.filter(obs => obs !== observer);
  }

  notificar(dados) {
    this.observers.forEach(obs => obs.atualizar(dados));
  }
}

class NotificacaoPushObserver {
  atualizar({ tipo, post, atorInteracao, detalhe = null }) {
    const autorDoPost = post.autor.nome;

    if (tipo === "comentario") {
      console.log(`🔔 [PUSH para ${autorDoPost}]: ${atorInteracao.nome} comentou. Disse: "${detalhe}"`);
    } else if (tipo === "curtida") {
      console.log(`🔔 [PUSH para ${autorDoPost}]: "${post.titulo}" recebeu curtida de ${atorInteracao.nome}.`);
    }
  }
}

class NotificacaoEmailObserver {
  atualizar({ tipo, post, atorInteracao }) {
    const autorDoPost = post.autor.nome;
    if (tipo === "comentario") {
      console.log(`📧 [E-MAIL para ${autorDoPost}]: Novo comentário de ${atorInteracao.nome} em "${post.titulo}".`);
    }
  }
}
```

**b) Exemplo de uso com inscrição, eventos e desinscrição**
```javascript
const profAltair = new Usuario(1, "Prof. Altair");
const alunoJoao  = new Usuario(2, "João Silva");
const alunaMaria = new Usuario(3, "Maria Souza");

const postRedesNeurais = new Post(101, "O que é um Perceptron?", "...", profAltair);

const servicoPush  = new NotificacaoPushObserver();
const servicoEmail = new NotificacaoEmailObserver();

postRedesNeurais.inscrever(servicoPush);
postRedesNeurais.inscrever(servicoEmail);

postRedesNeurais.adicionarCurtida(alunoJoao);
postRedesNeurais.adicionarComentario(alunaMaria, "Excelente explicação!");
postRedesNeurais.adicionarComentario(profAltair, "Fico feliz em ajudar!");

postRedesNeurais.desinscrever(servicoPush);
console.log("Push desativado para este post.");
```
